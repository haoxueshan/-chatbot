## 此前的队列积压中断

2026-11-01用户长录音复检：同一真实会话的三条识别流分别运行约31分钟、9分钟、2分半，累计采音42分22秒，保存242条原文版本以及三段WAV。均出现audio_backlog；其中两次清理时的WebSocket关闭码1006/1000覆盖了原始错误。现有历史记录不足以确定具体网络或发送阻塞原因，不能断言是固定时长上限、额度不足或密钥错误。

本轮修复：

- 准备阶段等待上游task-started后再开始PCM采集，避免冷启动占满队列；准备中可取消。
- 音频接收处理主动让出调度，避免突发包使健康发送任务得不到执行机会；保留约2秒队列硬上限。
- 同时监测发送与接收，发送失败即时退出；单次音频发送最长等待ASR_SEND_TIMEOUT_SECONDS（默认5秒）。不自动重试付费识别任务。
- 先回收子任务再关闭连接；保留首个失败，取消时的1000/1006不覆盖原始错误。
- 安全诊断写入processing.failed事件及capture_failed日志，不记录密钥、字幕、原始音频或供应商原始错误文本。

更新后，在PyCharm停止并重新运行backend/main.py，再刷新iPad页面。仍使用原HTTPS地址。开始录音后等待“正在准备识别服务”提示消失、计时开始，再说话。

若再次中断，在PyCharm终端寻找`capture_failed`：

| 字段/代码 | 用途 |
| --- | --- |
| audio_backlog | 音频队列达到2秒，采集被保护性停止 |
| upstream_send_timeout | 单次向阿里云发送超时 |
| upstream_disconnected / upstream_close_code | 上游连接关闭，保留关闭码但不暴露原始原因文本 |
| last_send_age_ms / send_wait_ms | 最近发送是否长时间停顿 |
| last_upstream_event_age_ms | 上游是否仍在返回识别或心跳消息 |
| queued_audio_ms / sent_audio_ms | 停止时积压量和已转发音频量 |

底部42:22这样的值是累计采音；字幕中的43:xx是含暂停的时间轴，二者可以不同。字幕和缺口按时间混排，不再把所有旧缺口放到最新字幕后。旧缺口仍保留以说明当时的中断。

本次验证使用本地故障注入和模拟界面，未新增付费调用。不能将其写成真实105分钟稳定性通过；新代码仍需真实网络长录音复验。
