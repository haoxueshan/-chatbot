# 实时音频稳定性验证（2026-11-05）

基线：`6e0c638fd663f9f96ef2d335966a05f4612b0783`。本轮仅 Mock，无付费 API 调用。

## 调用链与修复

`AudioWorklet → AudioCapture → useLive → LiveCapture.audio → audio_iter → stream_asr.send_audio`

上游结果由独立 reader 放入有界结果队列，再交给 `consume` 串行提交原文和 Outbox；浏览器临时字幕由单个发送任务处理。原来的同步查库、逐帧 WAV 写入、等待浏览器发送都会拖慢实时事件循环或上游读取。

- 收音不再查库；权限、会话状态及后台任务数量由一个每秒维护任务复核。SQLAlchemy Session 均在线程内创建、关闭。同一采集的写事务通过锁保持串行。
- WAV 使用单个维护任务每 100 ms 批量写入，包含写入中的字节仍计入容量；取消必须等待已开始的写入，写失败不能冒充成功。
- ASR sender 与 reader 独立，结果队列容量 64，满载等待消费者，不丢 final。一个 reader 手中最多另有一条待入队结果；保留原上游 WebSocket 自身接收限制。
- 临时 UI 队列最多 401 个身份，只合并同一身份的完整可替换快照；原文版本、待恢复原文和正式事件独立维护。浏览器发送（包括等待发送锁）限时 10 秒，失败停止采集并排空已接收结果。
- 停止信号不等待向满队列插入标记；达到时长上限也先停止接收新帧，再排空已接收 PCM，发送 finish-task 并等待上游定稿。异常、准备取消、存储失败及连接清理均有回归覆盖；不自动重开 ASR。
- Worklet 保留原重采样和 DSP，20 ms 分帧改用固定写入缓冲。浏览器背压检查包含即将发送的帧，停止后解除 Worklet 消息回调并拒绝旧采集帧。

## 容量与指标

PCM16LE / 16 kHz / mono：32 字节/ms，640 字节/20 ms。浏览器待发送字节和服务器待转发字节各限 64,000，保留约两秒预算。浏览器 bufferedAmount 还可能含控制消息，因此该检查是保守上限。

服务器不再叠加旧 `audio_max_queue_frames=100` 的帧数阈值；合法短帧也由总字节限制。队列结构另以最小合法 2 字节帧计算 32,000 个节点上限，常规 640 字节帧仍最多积压 100 帧。WAV 待写/在写字节另限 64,000。

| 指标 | 含义 |
|---|---|
| received_audio_ms | 已通过校验并被服务器接收的 PCM 字节 / 32 |
| queued_audio_ms | 服务器队列内尚未取出的字节 / 32，不含正在发送的一帧 |
| queue_frames | 队列内实际音频消息数，不计停止标记 |
| audio_queue_peak_ms | 本次采集的服务器队列峰值 |
| archive_queue_ms | 等待写入与正在写入的保留音频 |
| sent_audio_ms | 上游 ws.send 已完成的 PCM 字节 / 32，**不代表云端已确认识别** |
| send_wait_ms | 最近一次上游音频发送调用的等待时间 |
| last_send_age_ms | 距上一次音频发送完成的时间 |
| last_upstream_event_age_ms | 距最近读取上游消息的时间 |
| last_transcript_age_ms | 距最近读取包含文字的 ASR 结果的时间 |

## 限制

- 线程化不会使永久卡死的数据库或文件系统操作可强制终止；清理会等待在途事务/写入，底层长时间故障仍可能拖延停止。
- 结果队列持续满载时仍会对上游读取产生背压，不保证无限慢数据库下不中断。
- 未验证真实 API、实体 Safari、真实网络及 60 分钟课堂；未证明所有物理麦克风采样完整。本轮证明的是 Mock 已接收完整 PCM 帧的顺序、排空及异常行为。
